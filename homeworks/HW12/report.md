# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Датасет: `S12-hw-dataset.csv`, задача: прогноз `target` на 1 шаг вперед.
- Разбиение выполнено по времени: `train / validation / test`, без перемешивания.
- Сравнены подходы `B1` (`naive-last`), `B2` (`moving-average`), `B3` (`ridge-lag-features`), `R1` (`gru-forecast`).
- Лучшая модель выбирается по `best_val_mae` из `artifacts/runs.csv`, затем один раз оценивается на test.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: `hourly` (по колонке `date`)
- Горизонт прогноза: `1` шаг
- Размер датасета: `4320` наблюдений
- Диапазон дат: `2025-01-01 00:00:00` — `2025-06-29 23:00:00`
- Есть ли дополнительные внешние признаки: нет (используется сам ряд + производные признаки)
- Комментарий (2-4 предложения): ряд имеет выраженную внутрисуточную структуру (данные почасовые), а также медленные изменения уровня на более длинных промежутках. Это делает наивный прогноз приемлемым как стартовую точку, но ограничивает его на участках смены локального режима. Пропусков в данных нет (`date: 0`, `target: 0`), поэтому основной фокус — корректная валидация по времени и контроль утечек при генерации признаков.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: хронологически, индексы `0:70%`, `70%:85%`, `85%:100%`.
- Какие доли или интервалы использовались: `70% / 15% / 15%`.
- Почему `random split` здесь некорректен: перемешивает прошлое и будущее, создаёт leakage и завышает качество.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: `lag_1`, `lag_7`, `lag_14`.
- Какие rolling-признаки использовались: `rolling_mean_7`, `rolling_std_7` (по `target.shift(1)`).
- Какие календарные признаки использовались: `day_of_week`, `hour`.
- Как обрабатывались пропуски после построения лагов/rolling: строки с `NaN` удалялись (`dropna`).
- Использовалось ли масштабирование и где именно оно обучалось:
  - для `B3` (`Ridge`) — `StandardScaler` только на `X_train`;
  - для `R1` (`GRU`) — `StandardScaler` только на train-части таргета.

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): прогноз равен последнему известному значению.
- B2 (`moving-average`): прогноз по скользящему среднему из окна `24`.
- B3 (`ridge-lag-features`): `Ridge(alpha=1.0)` на lag/rolling/calendar признаках.
- R1 (`gru-forecast`): `GRU(hidden=64, num_layers=1)` на оконном представлении `window_size=24`.

Дополнительно:

- Основная метрика выбора лучшей модели: `MAE` на validation (`best_val_mae`).
- Дополнительные метрики: `RMSE`, `MAPE`.
- `window_size` для `GRU`: `24`
- Batch size: `64`
- Максимальное число эпох: `40`
- Optimizer: `Adam`
- Learning rate: `1e-3`
- Как сохранялась лучшая модель: `state_dict()` с минимальным `val_MAE` в `./artifacts/best_gru.pt` (лучшая эпоха по validation: `40`, см. `./artifacts/best_gru_config.json`).

## 7. Анализ

Наивный baseline `B1` оказался не провальным, потому что в ряде есть сильная локальная инерция: соседние точки близки, и прогноз «следующее равно предыдущему» уже дает разумный ориентир.  
`Moving average` (`B2`) в текущей постановке с окном `24` сработал заметно хуже: усреднение сглаживает динамику и запаздывает при локальных разворотах/скачках уровня.  
`Ridge` на лаговых, rolling- и календарных признаках (`B3`) улучшила качество относительно `B1`, потому что одновременно учитывает краткосрочную память (`lag_1`) и периодичность (`lag_7`, `lag_14`, `hour`, `day_of_week`).  
Также rolling-признаки помогли модели адаптироваться к текущему масштабу и волатильности процесса.  
`GRU` (`R1`) дала лучший результат на validation, потому что оконное представление позволяет извлекать нелинейные зависимости по последовательности, а не только линейную комбинацию вручную заданных признаков.  
На ряде заметны как минимум сезонная составляющая внутри суток и медленный дрейф уровня, поэтому последовательностная модель имеет дополнительное преимущество.  
Ключевые точки потенциальной утечки: случайное перемешивание до split, использование будущих значений при построении lag/rolling и `fit` масштабирования на всем датасете.  
В работе эти риски закрыты: split строго временной, `rolling` построен через `shift(1)`, а масштабирование обучается только на train-части.  
Выбор лучшей модели по validation принципиален, потому что test должен имитировать реально «невидимое будущее» и использоваться один раз для честной финальной оценки.  
Наиболее показательные ошибки наблюдаются на переходах между локальными режимами ряда (резкие изменения), где простые baseline запаздывают сильнее, а `GRU` лучше подхватывает форму динамики.

## 8. Итоговый вывод

Для этого датасета базовым production-кандидатом я бы выбрал `R1 (GRU)`, так как она показала лучшие метрики на validation и уверенный результат на test.  
Если нужна максимально простая и интерпретируемая модель с низкой стоимостью обучения/инференса, то `B3 (Ridge + lag/rolling/calendar)` уже дает сильный baseline и может быть достаточной.  
Переход к `GRU` особенно оправдан, когда в ряде есть нелинейная динамика и выраженные паттерны в последовательностях, которые линейная модель описывает ограниченно.  
Главный вывод: для временных рядов качество модели имеет смысл обсуждать только при корректной валидации по времени и жестком контроле утечек; иначе метрики становятся оптимистичными и непереносимыми на реальное будущее.
