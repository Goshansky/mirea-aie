# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

## 1. Кратко: что сделано

- Чанкинг: скользящее окно по символам, **`CHUNK_SIZE=380`**, **`CHUNK_OVERLAP=90`**.
- Векторизация: **`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`**, нормированные эмбеддинги, индекс **FAISS IndexFlatIP** (косинусная близость через скалярное произведение).

- Mini-RAG: **6** примеров в `./artifacts/rag_examples.csv` (экстрактивный ответ + источники).

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- Embedding-модель: **`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`**.
- Метрика сходства: скалярное произведение **L2-нормированных** векторов (эквивалент косинусному сходству).
- Индекс FAISS: **IndexFlatIP** по полной матрице чанков (точный поиск ближайших соседей).
- **top_k**: **5** для оценки контрольных запросов; **3** в демо-блоке; **4** в mini-RAG.
- Первые примеры retrieval: в ноутбуке для запросов про venv, Docker Compose, секреты в Actions, pre-commit выводятся top-3 с `doc_id` и score.

### 4.2. Контрольные запросы и оценка retrieval

- Число контрольных запросов: **10**.
- Релевантность: один ожидаемый **`doc_id`** на запрос; **hit@5** = 1 для всех строк в `./artifacts/retrieval_eval.csv`; **recall@5** по строкам = **1.0** (один чанк на документ — полный «вспомнить документ» в top-5).
- Метрики (усреднение по 10 запросам): **hit@5 = 1.0**, **recall@5 = 1.0**, **MRR@5 ≈ 0.9333** (из вывода `metrics_main` / последней JSON-сводки).
- Дополнительно: в таблице оценки — **`rank_of_first_relevant`**: для большинства запросов **1**, для запроса *«Что запускается при git push в CI?»* релевантный **`ci_cd`** впервые на **3**-м месте в top-5 (ожидаемо из-за пересечения с Git/GitHub).
- Простые запросы: с прямым совпадением терминов (**conda**, **pytest** + параметризация, **gpu_docker**, **logging**).
- Проблемный случай: *«Что запускается при git push в CI?»* — золотой документ не на первой позиции (**ранг 3**), хотя **hit@5** остаётся 1.

## 5. Эксперимент по параметрам retrieval и обновление базы знаний

- Сравнивался параметр **`CHUNK_SIZE`** при **`CHUNK_OVERLAP=90`**.
- Варианты: **280** и **480** символов.
- Результаты (вывод ячейки эксперимента):  
  - `chunk_size=280` → **hit@5 = 1.0**, **recall@5 = 1.0**, **MRR@5 = 0.875**  
  - `chunk_size=480` → **hit@5 = 1.0**, **recall@5 = 1.0**, **MRR@5 ≈ 0.9333**  
  Основная конфигурация **380** совпадает по **MRR@5** с вариантом **480** в этом прогоне.
- Выбор основного варианта: оставлен **`CHUNK_SIZE=380`** как компромисс между размером фрагмента и числом чанков; по **MRR@5** предпочтительнее более крупный чанк (**480**), что согласуется с тем, что **380** ближе к **480**, чем к **280**.
- Обновление базы: добавлены документы **k8s_basics**, **helm**, **prometheus**.
- Переиндексация: полный чанкинг **18** документов + новые эмбеддинги + новый **IndexFlatIP**.
- Изменения retrieval: по `./artifacts/retrieval_before_after_update.csv` для всех **5** запросов списки уникальных источников в top-5 **различаются** (`changed=True`): например, для запросов про Kubernetes / Helm / Prometheus в выдаче после обновления появляются **`k8s_basics`**, **`helm`**, **`prometheus`**.

## 6. Mini-RAG и результаты

Ссылки на файлы в репозитории:

- Оценка retrieval: `./artifacts/retrieval_eval.csv`
- Примеры ответов mini-RAG: `./artifacts/rag_examples.csv`
- Сравнение до/после обновления: `./artifacts/retrieval_before_after_update.csv`

Короткая сводка:

- Контекст: top-**4** чанка; ответ — **экстрактивный** (первые предложения из top-1 + строка про смежные `doc_id`).
- Генерация: без тяжёлой LLM, только из извлечённого текста.
- Источники: строка **`doc_id`** через **`|`** (см. столбец **`retrieved_sources`** в CSV).
- Удачные примеры: вопросы про **Prometheus pull-модель**, **Helm / staging vs production**, **pod vs deployment** — в источниках ожидаемые **`prometheus`**, **`helm`**, **`k8s_basics`**.
- Пограничный случай: вопрос про **correlation id** — top-1 остаётся **`logging`** (релевантно), но ответ смешивает общие уровни логирования; строгой связки «correlation id» с одним абзацем в базе нет (ограничение корпуса и экстракции).
- Роль retrieval: ответ целиком определяется top-чеками; при неверном top-1 экстрактивный ответ уехал бы по смыслу.

## 7. Анализ

На этом прогоне база и короткие документы дали **идеальные hit/recall по документу** при **k=5**, но **MRR** и **ранг первого релевантного** показывают, что запросы вроде *git push + CI* конкурируют с несколькими близкими темами (**git_basics**, **git_remote** раньше **ci_cd**). Эксперимент с **`CHUNK_SIZE`** подтвердил рост **MRR@5** при переходе с **280** к **480** при неизменных hit/recall. Обновление базы заметно меняет состав источников (все **5** сравнений с **`changed=True`**), что видно по появлению **Kubernetes/Helm/Prometheus**. Mini-RAG честно экстрактирует из top-1; «ошибки» чаще выглядят как неполнота формулировки или отсутствие узкого предложения в базе (correlation id), а не провал FAISS. Ограничения: один индекс без reranking, одна embedding-модель, нет генеративного перефразирования.

## 8. Итоговый вывод

Для учебной постановки разумно оставить связку **нормированные эмбеддинги `sentence-transformers` + FAISS `IndexFlatIP` + фиксированный k**, с явным списком источников в mini-RAG. По этому запуску качество retrieval формально высокое (**hit@5 = recall@5 = 1**), но **MRR** и ранги полезны, чтобы не переоценивать «успех» на пересекающихся темах. Связь с mini-RAG: пока top-1 релевантен, экстрактивный ответ устойчив; расширение базы улучшает покрытие новых тем, но меняет конкуренцию чанков и состав top-k для старых формулировок.
